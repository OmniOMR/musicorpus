# Repository layout

This repository holds a document and a python package that serves it, released separately — see [Versioning and releases](versioning-and-releases.md).

```
musicorpus/
  spec/              the MusiCorpus specification, and the script that renders it
  src/musicorpus/    the python package
  tests/             unit tests and the two fixture datasets
  docs/              documentation for the code
  .github/           the CI workflow
  musescore/         generated — MuseScore is downloaded here by the exporters
```

`spec/` sits at the top level rather than inside `docs/` because the specification is the point of the repository; the code exists to serve it. `spec/build.py` renders the document to HTML and PDF with pandoc and chromium — both outputs are gitignored and published as release assets instead.


## Inside the package

```
src/musicorpus/
  __init__.py        the public API
  dataset.py         reading a dataset: Dataset, Page, Subdivision, Sample
  manifest.py        musicorpus.json
  splits.py          splits.json
  layout.py          layout.json
  page_metadata.py   metadata.json
  image_subdivisions.py, coco.py, mung_to_coco.py
  cli/               one module per subcommand, plus run.py which registers them
  validation/        checking a dataset against the specification
  statistics/        aggregating dataset statistics
  exporters/         one subpackage per dataset that gets exported into the format
```

Three arrangements in there are deliberate and worth knowing.

**`__init__.py` is the public API.** It re-exports the names a library user needs and nothing else. Everything below it is internal arrangement that may move between versions. See [Python API](python-api.md).

**The base install declares no dependencies.** The modules describing the format are standard library only, so `pip install musicorpus` cannot conflict with a consumer's environment; mung, pycocotools, lmx, music21 and OpenCV live behind the `validation`, `statistics` and `exporters` extras. The reader parses the JSON formats MusiCorpus itself defines and hands back a `Path` for everything else, which is what makes that possible. `tests/test_dependencies.py` imports each format module in a fresh interpreter and fails if it reached an optional package.

**No command imports anything heavy at module level.** Every CLI command defers its imports into `execute` and wraps them in `cli/extras.py:requires`, which keeps `musicorpus --help` at about four hundredths of a second rather than four tenths, and turns a missing extra into the command that installs it rather than a traceback. [A test](../tests/test_cli.py) guards both.


## Why `src/`

The package sits in `src/` rather than at the repository root, which costs a directory level and means it must be installed — `pip install -e .` — before anything can import it.

It earns that here because the package ships non-python data: the OmniOMR exporter's `assets/` folder, loaded relative to `__file__`. Without `src/`, a `musicorpus/` folder at the root would be on `sys.path` for anything run from the repository root, and `import musicorpus` would resolve to the source tree whether or not anything was installed — so a build change that dropped those assets from the wheel would be invisible. Development runs would read them off disk, tests would pass, and the breakage would appear only for somebody installing from the git URL. With `src/`, an import can only resolve to the installed distribution, and [the CI wheel job](../.github/workflows/checks.yml) opens the built wheel to check the assets are in it.


## Tests

`tests/` holds unit tests only; the whole suite runs in about a second and a half.

`tests/data/` holds two synthetic datasets, both generated by `build_test_fixture.py` and committed rather than built during the test run, so they can be inspected and diffed:

- **`TEST.Valid`** conforms to the specification in every respect the validator checks, so `musicorpus validate` reports zero errors on it. The validator tests copy it and break one thing at a time.
- **`TEST.Fixture`** bends the rules on purpose — a page with only an image and a transcription, a page in no split, a split naming a page that is not on disk, an image variant, a png-only page. The reader tests need those cases; `test_validation.py` pins which complaints the validator makes about it.

Both are also worked examples: a few dozen kilobytes that a dataset author can lay their own tree against.

What is *not* covered is the exporters. They are coupled to input data nobody outside the project has — MuNG Studio backups, MuseScore editions — so there is nothing to run them against in a unit test. They are reference implementations rather than product; see [the README](../README.md#cli).
